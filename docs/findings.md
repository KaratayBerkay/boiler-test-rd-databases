# Findings (verified in this lab, Sept 2026; numbers are p50 unless stated; Docker Compose on one host unless the section says k3s)

Full tables: `results/SUMMARY.md`. Per-engine raw data and plans: `results/<engine>/latest.json`, `results/<engine>/plans/`.

## SQL capabilities
- Window functions, recursive CTEs and JSON extraction work on every engine except: recursive CTEs missing in CrateDB/QuestDB; LATERAL missing in MariaDB, SQLite, ClickHouse, Firebird, H2, MonetDB, CrateDB, QuestDB (portable fallback: ROW_NUMBER in a derived table, which every engine ran).
- `GROUPING SETS`: not in CockroachDB, SQLite, QuestDB, CrateDB (MySQL/MariaDB only via `WITH ROLLUP`).
- `MERGE`: PostgreSQL 15+, SQL Server, Oracle, Db2, Firebird, MonetDB, DuckDB (1.1+); MySQL/MariaDB/TiDB/SQLite/CockroachDB/ClickHouse use engine-specific UPSERT instead.
- `PERCENTILE_CONT`: missing in MySQL/TiDB/SQLite/Firebird/H2; CockroachDB only over FLOAT8; MariaDB only as a window function; QuestDB `approx_percentile` (1.6 s on 200k rows vs 20-170 ms elsewhere).
- Row-value comparison `(a,b) > (x,y)`: PostgreSQL turns it into an index seek (0.64 ms vs 44 ms for the OR-expanded form); MySQL 9 does the opposite (166 ms vs 9 ms); SQLite/DuckDB/CockroachDB handle both.
- `QUALIFY` is DuckDB/ClickHouse-only; `DISTINCT ON` PostgreSQL-family + DuckDB + ClickHouse. QUALIFY crashed the MonetDB session (server closed connection).
- Isolation semantics differ: PostgreSQL rejects the second writer at REPEATABLE READ (40001); MySQL 9 lets it through (lost-update semantics, final balance 80 = both applied); MariaDB 11.8 rejects with error 1020 (innodb_snapshot_isolation); MySQL SERIALIZABLE turns the read into a shared lock and blocks the other writer for `innodb_lock_wait_timeout` (50 s default); DuckDB and SQLite (WAL) abort the stale writer immediately ("Conflict on update!", "database is locked"); CockroachDB 40001 in both modes.
- Deadlock detection time: MySQL/MariaDB 1-2 ms (immediate wait-for graph), PostgreSQL 1001 ms (`deadlock_timeout`), CockroachDB immediate (40001), DuckDB immediate, SQLite has a single writer (second writer blocked).

## Optimisation
- Composite index order (equality first) beat the reverse order on every B-tree engine (PostgreSQL 2.3 vs 4.6 ms, MySQL 12 vs 17, SQLite 2.3 vs 7.6, CockroachDB 65 vs 107); ClickHouse's bloom-filter data-skipping index made no difference because the sorting key already prunes.
- Non-sargable `YEAR()/MONTH()` predicates cost 20-300x once an index exists (PostgreSQL 28 vs 1.4 ms, SQLite 116 vs 0.42 ms).
- OFFSET pagination at page 2000: 45-330 ms everywhere; keyset with an index: 0.1-9 ms.
- `NOT EXISTS` vs `LEFT JOIN ... IS NULL` vs `NOT IN`: PostgreSQL 12 / 81 / 99 ms, SQLite 2.7 / 36 / 1.5 ms; MySQL, CockroachDB, ClickHouse produce the same plan for all three.
- Insert batching: single-row autocommit 0.4k-6.7k rows/s; 1000-row multi-row VALUES in a transaction 6k-34k rows/s; ClickHouse 12 rows/s single-row (never do that) vs 2.8k batched; PyMySQL `executemany` silently degrades to per-row statements when VALUES contains a literal.
- Bulk load path matters more than the engine: COPY/LOAD DATA/read_csv/COPY INTO/HTTP import 100k-1.1M rows/s vs 30-90k rows/s with driver inserts; FK checks halve COPY speed (PostgreSQL order_items 42k vs events 129k rows/s).
- Prepared statements (psycopg `prepare=True`): 0.55 vs 0.85 ms per point lookup on PostgreSQL; psycopg already auto-prepares after 5 executions.

## Connections
- Connection cost: PostgreSQL 12 ms (fork + SCRAM), PgBouncer 8.8 ms, MySQL 1.3 ms, MariaDB 1.4 ms, CockroachDB 2.8 ms, TiDB 2.7 ms, Db2 4.2 ms, YugabyteDB 21 ms, Oracle Free 41 ms (dedicated server process), Firebird 85 ms (wire crypt handshake), SQL Server via pymssql/FreeTDS 175 ms, ClickHouse (clickhouse-connect) 33 ms, H2 PG-protocol 760 ms (and ~41 ms per statement afterwards), QuestDB 1.1 ms.
- Limits: PostgreSQL refuses with 53300 above `max_connections`; MySQL/MariaDB 1040; PgBouncer queues 5000 clients on 20 server connections; ClickHouse accepted 4106 idle HTTP connections.
- Throughput ceiling with 64 worker processes on this host (primary-key lookups): PostgreSQL 74k QPS direct vs 24k via a single PgBouncer (single-threaded); MySQL 59k direct / 42k via ProxySQL; MariaDB 54k / 22k via MaxScale; Galera node 57k; SQL Server 46k; YugabyteDB 36k; Db2 24k; TiDB 23k; CockroachDB 22k; MonetDB 20k; CrateDB 17k; Oracle Free 12-24k (2-thread cap); Firebird 5.7k; ClickHouse 3.1k and H2 1.6k (per-query overhead); Citus coordinator at 0.8 CPU 1.5-1.9k; QuestDB 54k; SQLite 637k (16 processes, WAL); DuckDB ~1k concurrent point lookups (not an OLTP engine).
- Bulk-insert load test (1000-row batches, 15 s, N processes; best rows/s): CrateDB 156k (32 conn), YugabyteDB 82k (16), TiDB 52-88k, PXC 62k, H2 53k, Db2 47k, SQL Server 27k, Firebird 21k, Oracle 19k, Citus 16k (0.8-CPU coordinator).
- Deadlock detection: MySQL/MariaDB/Galera 1.5 ms, DuckDB 1.2 ms, TiDB 6 ms, CockroachDB 104 ms, YugabyteDB 352 ms, PostgreSQL/Citus 1.0 s (`deadlock_timeout`), SQL Server 2.9 s (5-second detector), Oracle 3.3 s, Db2 5.7 s (`DLCHKTIME` 10 s), Firebird 10 s (`DeadlockTimeout`); MonetDB and SQLite never deadlock (optimistic / single writer).
- Read/write split: ProxySQL and MaxScale routed 100% of writes to the primary while serving reads from the replica; HAProxy round-robin sent 50% of writes to the PostgreSQL replica (25006).
- Python threads plateau at ~2.7k QPS (GIL); measurements above use forked processes.

## Citus sharded cluster (coordinator + 5 primaries + 5 replicas, 0.8 CPU / 1.5 GiB each, 3 PgBouncers behind HAProxy)
- Distributed `COPY` of the 1M-row events table through the coordinator: 140-189k rows/s (single PostgreSQL 18 with 2 GB shared_buffers and no CPU cap: 129k).
- Tables had to be hash-distributed on their primary keys (Citus requires PK/UNIQUE to include the distribution column), so joins between `orders`, `order_items` and `events` are repartition joins: anti-joins and cohort queries take 1.8-7.8 s versus 12-300 ms on single-node PostgreSQL. Colocating by `customer_id` (PK `(customer_id, id)`) is the fix in a real schema.
- Point lookups through the 0.8-core coordinator: 1.9k QPS at 4-32 connections, p99 rising from 1.7 ms (1 connection) to 444 ms (64 connections); via the PgBouncer tier 1.8k QPS with p99 capped near 95 ms because only 18 backends ever run.
- Multi-connection bulk insert into the hash-distributed `events` table (1000-row batches, 15 s per run, exact cgroup CPU during the inserts):

  - With INSERT ... VALUES the coordinator is the bottleneck: it parses and routes every row (100%+ of its cap) while the workers idle at ~25%; adding connections only adds queueing (batch p50 from 0.3 s to 12 s) and, direct, throughput *drops* to 6.9k rows/s at 64 connections. Through the PgBouncer tier (3 x 6 server connections) throughput holds at ~12k because only 18 backends ever run on the coordinator.
  - `COPY` pushes the work to the workers (90-112% of their cap): 13-16k rows/s, the cluster's CPU ceiling at 0.8 core per instance (~4.8 cores in total).
  - Before tuning, 32 direct connections OOM-killed the 1.5 GiB coordinator (each backend fanned out up to 16 connections per worker with 25-connection PgBouncer pools). `citus.max_adaptive_executor_pool_size=4`, `citus.max_cached_conns_per_worker=1` and `DEFAULT_POOL_SIZE=6` per PgBouncer fixed it (coordinator peak 0.7-1.5 GB, no kills).
  - Next scaling steps: more coordinators (Citus MX: run queries from workers or add `shouldhaveshards=false` nodes) behind the pooler tier, colocated distribution keys, and raising the per-instance CPU cap for the coordinator.
- Worker failover (measured 1.59 s until a 32-row insert spanning every shard succeeded through the coordinator): `docker kill w1` -> `pg_ctl promote` on r1 -> on the coordinator `SET citus.enable_metadata_sync = off`, `citus_update_node(<r1 secondary nodeid>, 'r1-stale', 5432)` (frees the host:port), `citus_update_node(<w1 nodeid>, 'r1', 5432)`, `SET citus.enable_metadata_sync = on`, `start_metadata_sync_to_all_nodes()`; `citus_remove_node('r1-stale')` afterwards once metadata has synced. Doing `citus_remove_node`/`citus_update_node` with metadata sync on fails because Citus tries to reach the dead worker.

## Backup and recovery (every strategy executed as a drill: backup -> restore elsewhere -> fingerprint -> point-in-time probe; `results/SUMMARY.md` has the numbers)
- 49 strategies across the 20 engines, 48 executed and **verified** by fingerprint (the 49th is Oracle RMAN, absent from the slim image). 14 engines passed a point-in-time or incremental probe (the rows written after the full backup came back, the DELETE after the recovery point did not): true PITR on PostgreSQL, Citus, MySQL, MariaDB, TiDB, CockroachDB, YugabyteDB, SQL Server, Oracle (flashback) and Db2; incremental-chain probes on ClickHouse, CrateDB, Percona XtraDB Cluster and Firebird. No point-in-time mechanism at all: QuestDB, MonetDB, H2, SQLite (Litestream would add it), DuckDB.
- Logical dumps are small and slow to restore, physical copies are big and fast: at scale 1 PostgreSQL `pg_dump -Fd -j4 --compress=zstd` writes 32 MB in 2.7 s and `pg_restore -j4` needs 10.6 s, while `pg_basebackup` copies the 270 MB cluster in 2.5 s and the copy is serving queries 3.8 s later; MariaDB `mariadb-dump` 148 MB / 27 s restore vs `mariadb-backup` 727 MB / 4.8 s to a running instance; MySQL Shell dump 32 MB / 20 s restore vs clone 426 MB / 2.2 s; SQL Server full backup 690 MB compressed in 16 s, restored in 26 s; Db2 offline image 160 MB / 10.5 s restore; QuestDB's checkpoint copy is the whole 1.26 GB root.
- The "latest" tools earn their keep: the PG17+ incremental backup (`summarize_wal`) was 21 MB against a 270 MB full copy (8 %) and `pg_combinebackup` restored it in 2.2 s without any extra tooling; MySQL Shell `dumpTables` + `loadDump` (4 threads, zstd) produced a 5x smaller artifact than `mysqldump` (32 vs 146 MB) and restored twice as fast (20 vs 40 s); CockroachDB `BACKUP ... WITH revision_history` + `RESTORE ... AS OF SYSTEM TIME` (3.1 s) and YugabyteDB snapshot schedules (`restore_snapshot_schedule`, 3.3 s in place) give PITR without any log shipping; TiDB `FLASHBACK CLUSTER TO TIMESTAMP` rolled the whole cluster back in place in 42 s (the SQL `BACKUP`/`RESTORE` statements run BR inside tidb-server; the `br` binary is only needed for log backups).
- GTID-bounded replay is the cleanest MySQL-family PITR: a clone or mariadb-backup restore made a replica of the source with `START REPLICA UNTIL SQL_BEFORE_GTIDS` / `START SLAVE UNTIL master_gtid_pos`, which stops exactly before the bad transaction (the official `mysql:9` image has no `mysqlbinlog`). MariaDB additionally undid the DELETE in place with `mariadb-binlog --flashback` in ~0.2 s.
- SQL Server is the most operator-friendly PITR: `BACKUP LOG` + `RESTORE LOG ... WITH STOPAT` worked first time inside an Availability Group; Db2 needs the most ceremony (offline backup after switching to `LOGARCHMETH1`, `TRACKMOD ON`, manual incremental chain, `ROLLFORWARD ... OVERFLOW LOG PATH`), and its `INCREMENTAL AUTOMATIC` picked a deleted image once - the manual chain is deterministic.
- Oracle Free (slim image) has Data Pump and Flashback but no RMAN binary; Data Pump has ~60 s of fixed overhead even for a 35 MB schema. Flashback needs > 5 s between a DDL and the flashback point (ORA-01466 from the 3 s SCN/time mapping).
- Restore-under-a-new-name is not universal: ClickHouse needs `{uuid}` in the Keeper path (explicit `{database}` paths collide with `REPLICA_ALREADY_EXISTS`); TiDB BR and CrateDB (without the rename options) restore in place, so the drill drops a table first; DuckDB `COPY FROM DATABASE` copies tables alphabetically and violates foreign keys.
- Container details that broke restores: a PostgreSQL scratch instance must match the primary's `max_connections` (hot standby refuses recovery otherwise); MariaDB 11 renamed `xtrabackup_binlog_info` to `mariadb_backup_binlog_info`; a fresh MonetDB database starts with the password `monetdb`; the Db2 compose healthcheck holds a CLP connection so offline backups must retry; QuestDB's image has no `tar`; Firebird's `nbackup` must run as the owner of the `.fdb` (root in the official image).
- Citus: `citus_create_restore_point()` writes one named restore point on the coordinator and every worker (2PC blocked meanwhile); restoring all six nodes to it in containers that reuse the node names as network aliases brings the cluster back with its `pg_dist_node` metadata intact (564 MB of base backups + WAL, ~8 s restore at scale 1).

## Logging (slow-query capture, audit trail, cost of logging everything; `results/SUMMARY.md` "Logging" table)
- Every engine captured the tagged ~300 ms statement in its slow-query sink within 1.1 s (SQL Server's Extended Events took 2.3 s = `MAX_DISPATCH_LATENCY`) and filtered the fast one; every engine with an audit facility recorded the tagged DDL. Engines whose sink has no threshold (DuckDB QueryLog, ClickHouse query_log, CrateDB jobs_log, QuestDB `_query_trace`) log everything cheaply because the sink is an in-memory/async table.
- Logging **every** statement costs between "nothing measurable" and most of the throughput: PostgreSQL text + JSON 13 % (1.5 KB per statement across both sinks), MariaDB slow log at `long_query_time=0` 7 %, MySQL within noise, Percona's `log_slow_verbosity=full` 21 %, Oracle `DATABASE_TRACE_ENABLE` 24 %, DuckDB QueryLog 22 %, the CPU-capped Citus coordinator 46 %, SQLite application-side JSONL 72 % (a 3 us statement vs a JSON line), Firebird's trace session 73 %, Db2's activity event monitor 13 %, CockroachDB admin audit with an admin application user writes 1.5 KB per statement (73 MB in a 4 s test) - use a non-admin app role. ClickHouse, QuestDB, CrateDB, MonetDB, YugabyteDB, TiDB and SQL Server stayed within 0-8 %. Differences under ~10 % were within run-to-run noise on the shared host (another lab's cluster was being built on it during these runs).
- Structured logs are available almost everywhere but rarely on stdout: PostgreSQL `jsonlog` and MySQL `log_sink_json` need files (the collector takes over stderr), ClickHouse and CockroachDB can do JSON to both file and console, TiDB `log.format=json` on stdout. The Docker `json-file` driver (50 MB x 3, compressed) is the outer layer for all of them.
- Settings frozen at start bite during incidents: PostgreSQL `postgres -c` options outrank `ALTER SYSTEM` (moved into `postgresql.conf` via the init script); Percona `audit_log_*` variables need the `loose-` prefix (`--initialize` runs without plugins); Firebird's audit trace config is read at server start and its `database =` line is a regex; CockroachDB cluster settings take a few seconds to reach the nodes and v26 routes `slow_query` events to SQL_EXEC rather than SQL_PERF; H2 forgets `QUERY_STATISTICS` when the last connection closes.
- Audit facilities differ in what they are: PostgreSQL/YugabyteDB `log_statement=ddl` (pgaudit where bundled), MariaDB `server_audit`, Percona `audit_log` JSON, SQL Server Audit files, Oracle unified auditing, Db2 audit policies (`AUDIT DATABASE USING POLICY` only took effect from the CLP, not through ibm_db), CockroachDB SENSITIVE_ACCESS channel with `EXPERIMENTAL_AUDIT` per table (tables are `schema_locked` by default in v25+), TiDB `ADMIN SHOW DDL JOBS` (audit plugin is Enterprise), MySQL Community has none (general log only).

## Kubernetes (k3s via k3d, local Harbor; `docs/kubernetes.md`, `docs/kubernetes-backup-logging.md`, `results-k3s/`)
- All 17 containerized stacks deploy from generated manifests and reach Ready on one k3d node (`k8s/scenarios.sh verify-all`): single nodes in 15-30 s, primary/replica/proxy stacks in 28-70 s, the multi-node clusters in 65-160 s (Citus with 16 pods 122 s, Db2 159 s, PXC 128 s).
- Two things Docker does implicitly broke on Kubernetes: (1) a generator that defaults the pod `hostname` to the compose service name crash-looped MaxScale (`monit` registers a `check system <hostname>` and the name collided with its own `maxscale` service) - only set a hostname the compose file declares; (2) a PVC mounts *empty* where a Docker named volume is seeded from the image, so the Oracle faststart image lost its baked database (`ORA-01081` after the stale `/dev/shm` SGA persisted across restarts) - an initContainer seeds the PVC and clears `/dev/shm` (`x-k8s: seed_from_image`, `shm_reset`). A failing startupProbe *kills* a slow-booting database where a compose healthcheck merely marks it unhealthy: give it the real first-boot budget.
- Kubernetes self-heal is not failover: deleting the PostgreSQL primary pod brought it back Ready on the same PVC in 5 s with replication re-established, but replica **promotion** (`k8s/scenarios-backup.sh promote`) took 6.4 s to the first successful write against 0.5 s with `docker kill` on compose - scaling the Deployment to 0 and pod deletion dominate, not `pg_ctl promote`.
- The backup and logging drills run unchanged on the cluster (`RDLAB_PLATFORM=k3s`): the throw-away restore containers become scratch Pods on the backup PVC with a NodePort, and every strategy of PostgreSQL, MySQL, ClickHouse and CockroachDB verified there (MySQL's clone Pod replayed the `source` Service's binlog to the GTID before the DELETE). CronJob backups (`backup-now`) took 4-6 s at scale 0.3; `verify-backups` 4/4 PASS. Restore times exclude image pull and scheduling on k8s (the scratch helper returns once the Pod is Running) while `docker run -d` returns before the process starts - do not compare the two columns directly.
- `kubectl exec` has no `-u`: every drill step that must run as the database OS user (pg_dump/pg_basebackup/`pg_ctl promote` as `postgres`, nbackup as the `.fdb` owner) is wrapped in `gosu`/`su` inside the pod. Per-container cgroup CPU/memory (the compose load test's best column) is not available under k3d because the containers live inside the node container.
- Engine log *files* on PVCs (jsonlog, slow logs, audit files) are invisible to `kubectl logs`; a `logs` sidecar tailing them (`logs-sidecar`) turns them into container logs that any node agent ships. The kubelet's `container-log-max-size`/`max-files` replace the Docker `json-file` rotation.
- Harbor as the only pull source: 24 images (34 GB) mirrored once, digests locked in `k8s/images.lock.json`; robot accounts (push+pull for CI, pull-only for the nodes) instead of the admin user; `crane copy` when Docker's containerd store refuses to push a multi-arch index it pulled; k3s' own system images need a `docker.io` mirror in `registries.yaml` or the first boot hits the Hub rate limit.

## Docker / tooling
- Docker Hub anonymous manifest limit (100/6h) is reached after ~1 image survey; `mirror.gcr.io` has no such limit.
- PostgreSQL 18 image: `PGDATA=/var/lib/postgresql/18/docker`, volume `/var/lib/postgresql`.
- MySQL 8.4/9: `innodb_log_file_size` removed (`innodb_redo_log_capacity`), `mysql_native_password` removed in 9.
- MariaDB official image configures replication from env but does not `START REPLICA`; healthcheck flags must precede `--replication`.
- CockroachDB 26.x restricts `crdb_internal` unless `allow_unsafe_internals=true`; `SET CLUSTER SETTING` cannot run in a multi-statement `-e`.
- ClickHouse HTTP sessions are stateless (`SET` does not persist); LEFT JOIN yields defaults unless `join_use_nulls=1`; `DELETE` is an async mutation.
- Firebird official image: connect with the full path `/var/lib/firebird/data/<db>.fdb`; the Python driver needs `libfbclient.so.2` on the host and inserts one row per round trip (~800 rows/s), hence scale 0.3; `SUM()` over NUMERIC(12,x) returns INT128 (NUMERIC(38,x)) which the driver cannot describe, so the lab stores decimals as DOUBLE PRECISION there.
- SQL Server container image: no Full-Text Search component (q13 falls back to LIKE); pymssql `bulk_copy` (BCP) writes Python strings into NVARCHAR columns as UTF-16 mojibake, so the lab loads with multi-row INSERTs (2.9k rows/s, FreeTDS parameter binding is slow); pymssql connect costs 175 ms.
- TiDB refuses index builds on a nearly full disk (`tidb_ddl_enable_fast_reorg` ingest checks free space in its temp dir): the lab sets `tidb_enable_dist_task = OFF` and `tidb_ddl_enable_fast_reorg = OFF`; TiKV pre-allocates ~9 GB per node unless `storage.reserve-space`/`raftstore.capacity` are lowered.
- CrateDB stops allocating shards above the 90% disk-usage high watermark (`cluster.routing.allocation.disk.watermark.*`); the lab raises them to 97/98/99%.
- YugabyteDB YSQL listens on the advertised address, not loopback: healthchecks must use `pg_isready -h $(hostname)`.
- Percona XtraDB Cluster: the entrypoint's temporary init server is socket-only; a TCP healthcheck prevents joiners from starting their SST against it and crashing.
- Docker Compose: a one-shot init service that is still *running* is not "ready" - the harness had to treat running one-shot containers as pending, otherwise SQL Server's AG setup (2 minutes) was raced by the load phase.
- The host disk sat at 94-98% during the runs; TiKV reservations, CrateDB watermarks and SQL Server logins all failed on it before the fixes above. 87 GB of the user's Docker build cache is reclaimable (`docker builder prune`), which was not touched.
- MonetDB healthcheck needs a `.monetdb` credentials file (`DOTMONETDBFILE`); pymonetdb in autocommit mode rejects explicit COMMIT.
- QuestDB: `count()` needs an alias in materialized views, no correlated subqueries, `LIMIT lo,hi` semantics differ.
