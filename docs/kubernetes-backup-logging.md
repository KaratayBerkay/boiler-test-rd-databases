# Backup, recovery and logging on the k3s runtime

Companion to [kubernetes.md](kubernetes.md) (cluster, Harbor, generated manifests, `k8s/scenarios.sh`). This layer adds
what a database platform needs *after* it is running on Kubernetes: scheduled backups into the stacks' backup volumes,
restore and point-in-time drills executed against the cluster, replica promotion, and a log-shipping path that turns the
engines' own JSON/slow/audit logs into container logs. Everything is additive - new files only, nothing in
`stacks/<engine>/k8s/` (regenerated by `k8s/gen.py`) is edited:

| path | what |
|---|---|
| `k8s/gen-backup-addons.py` | writes one CronJob per stack into `k8s/addons/backup/<stack>/` (kustomize dir, namespace `rdlab-<stack>`) |
| `k8s/addons/backup/<stack>/` | the CronJob: the engine's client image from Harbor, backup into the shared backup PVC (`/backups/cron/<ts>`), keeps 5 |
| `k8s/scenarios-backup.sh` | `list`, `schedule`/`unschedule`, `backup-now`, `artifacts`, `restore-drill`, `logging-drill`, `logs-sidecar`, `promote`, `verify-backups` |
| `harness/rdlab/k8s_scratch.py` | scratch restore **Pods** (the k8s form of the throw-away restore containers the compose drills use) |
| `harness/rdlab/util.py` (`RDLAB_RESULTS_DIR`) | cluster runs write to `results-k3s/` so they never overwrite the compose numbers |

## 1. Scheduled backups (CronJobs)

```bash
make -C k8s gen && k8s/scenarios.sh deploy postgres          # the stack itself (kubernetes.md)
uv run --project harness python k8s/gen-backup-addons.py     # (re)generate k8s/addons/backup/*
k8s/scenarios-backup.sh schedule postgres                    # CronJob backup-postgres in rdlab-postgres, "0 */6 * * *"
k8s/scenarios-backup.sh backup-now postgres                  # kubectl create job --from=cronjob/backup-postgres, wait, logs
k8s/scenarios-backup.sh artifacts postgres                   # ls -la /backups/cron in the primary pod
```

What each CronJob runs (all connect through the Service DNS name of the primary, all images are the ones already mirrored in Harbor):

| stack | image | command |
|---|---|---|
| postgres / citus | pgvector:pg18 / citus | `pg_dump -h primary -Fd -j 2 --compress=zstd` + `pg_dumpall --globals-only` |
| mysql | mysql:9 | `mysqlsh -- util dump-tables lab --all --threads=2 --compression=zstd` |
| mariadb | mariadb:11 | `mariadb-dump --single-transaction --routines --triggers --events --gtid \| gzip` |
| pxc | pxc:8.4 (uid 1001) | `mysqldump --single-transaction \| gzip` |
| tidb | mysql:9 client | `BACKUP DATABASE lab TO 'local:///backups/cron/<ts>'` (BR inside tidb-server; every TiKV pod mounts the PVC) |
| cockroach | cockroach | `BACKUP DATABASE lab INTO 'nodelocal://1/cron' WITH revision_history` (crdb1's extern dir; `SHOW BACKUPS` lists them) |
| yugabyte | yugabyte | `ysql_dump` + gzip |
| mssql | mssql (uid 10001) | `BACKUP DATABASE [lab] TO DISK ... WITH INIT, COMPRESSION, CHECKSUM` via sqlcmd (the server writes the file) |
| oracle | oracle-free (uid 54321) | directory object on `/backups/cron` + `expdp SCHEMAS=lab` |
| clickhouse | clickhouse-server | `BACKUP DATABASE lab TO Disk('backups', 'cron/<ts>')` |
| crate | crate | `CREATE REPOSITORY` (idempotent) + `CREATE SNAPSHOT lab_backups.cron_<ts> ALL` |
| monetdb | monetdb | `msqldump -h monetdb -d lab \| gzip` |
| firebird | firebird:5 | `gbak -b -g firebird:/var/lib/firebird/data/lab.fdb` |
| h2 | rdlab/h2 | `org.h2.tools.Shell ... -sql "BACKUP TO '/backups/cron/lab-<ts>.zip'"` |
| db2 | — | `backup-now db2` = `kubectl exec` `db2 backup db lab online to /backups/cron` (backups only run inside the instance) |
| questdb | — | `backup-now questdb` = `kubectl exec`: `CHECKPOINT CREATE` (HTTP), `cp -a db conf .checkpoint`, `CHECKPOINT RELEASE` |

Retention is `ls -1dt /backups/cron/* | tail -n +6 | xargs rm -rf` inside the job (KEEP=5); CockroachDB and CrateDB keep
their own catalogs (`SHOW BACKUPS`, `sys.snapshots`). The Jobs are pods like any other: `kubectl -n rdlab-postgres get jobs,pods
-l rdlab.io/addon=backup`, `kubectl logs job/...`.

## 2. Restore and PITR drills on the cluster

The compose backup phase (`docs/findings.md`, "Backup and recovery") restores every backup somewhere else and fingerprints
it. On k3s the same code runs with `RDLAB_PLATFORM=k3s`: `docker exec` becomes `kubectl exec` (`harness/rdlab/platform.py`),
and the throw-away restore *containers* become throw-away restore **Pods** (`harness/rdlab/k8s_scratch.py`):
a Pod in the stack namespace that mounts the same backup PVC, plus a NodePort Service on the nodePort `k8s/ports.json`
reserves for the stack's `backup.restore_port`, so the harness reaches the restored instance on `127.0.0.1:<nodePort>`
exactly like it reaches the primary.

```bash
k8s/scenarios-backup.sh restore-drill postgres      # = RDLAB_PLATFORM=k3s RDLAB_RESULTS_DIR=results-k3s rdlab phase postgres backup
k8s/scenarios-backup.sh logging-drill postgres      # the logging phase against the cluster
k8s/scenarios-backup.sh promote postgres            # replication phase with --failover: scale the primary Deployment to 0,
                                                    # pg_ctl promote in the replica pod, first successful write (data-plane failover)
```
Results land in `results-k3s/<stack>/latest.json` (+ `results-k3s/SUMMARY.md`), never in `results/`.

`kubectl exec` has no `-u`; the drill steps that must run as the database OS user (pg_dump/pg_basebackup as `postgres`,
nbackup as the file owner, `pg_ctl promote` as postgres) are wrapped in `gosu`/`su` inside the pod by `dockerctl.exec_in` (k3s branch).

## 3. Logging on the cluster

Kubernetes' native path is **stdout/stderr -> kubelet container logs** (`/var/log/pods`, rotated by the kubelet's
`containerLogMaxSize`/`containerLogMaxFiles`, collected by whatever node agent you run: Vector, Fluent Bit, Promtail/Alloy).
The stacks already log their *server* stream that way (ClickHouse and TiDB in JSON, CrateDB/QuestDB/CockroachDB OPS+HEALTH
JSON on stderr). Their **slow-query, JSON and audit files** live on the data PVCs; the sidecar scenario makes them container
logs too:

```bash
k8s/scenarios-backup.sh logs-sidecar postgres       # patches Deployment/primary with a `logs` container (busybox, tail -F of
                                                    # /var/lib/postgresql/log/*.json on the pg-primary PVC), rolls the pod
kubectl -n rdlab-postgres logs deploy/primary -c logs -f
```
Sidecar targets: postgres/citus jsonlog, mysql JSON error log + slow log, mariadb slow + server_audit log, pxc audit JSON +
slow log, tidb slow log, cockroach SQL_EXEC + SENSITIVE_ACCESS channels, yugabyte postgresql-*.log, mssql errorlog, db2
db2diag.log, monetdb merovingian.log, firebird audit trace, h2 trace file. Oracle's diag directory is not on a PVC (use
`kubectl exec ... tail -f .../alert_FREE.log`); ClickHouse already writes JSON to the console.

The `logging-drill` verb runs the harness logging phase on the cluster: slow-query capture proof, audit proof, cost of
logging every statement, and it records `kubelet` as the log driver (`platform.log_config`).

## 4. Verify everything

```bash
k8s/scenarios-backup.sh verify-backups               # backup-now on every deployed stack -> VERDICT <stack> PASS/FAIL
k8s/scenarios-backup.sh verify-backups mysql tidb    # a subset
```

## Measured on the k3d cluster (Sept 2026, scale 0.3, `results-k3s/`)

| stack | CronJob backup (`backup-now`) | restore drill (`restore-drill`) | other |
|---|---|---|---|
| postgres | `pg_dump -Fd` 9.3 MB in 4 s, retention applied | pg_dump / pg_basebackup / PG17 incremental / WAL PITR all verified; scratch Pods on the `pg-backups` PVC, restored copy answering on 127.0.0.1:30030 | logging drill: slow query captured in 0.45 s, DDL audited, logging everything 8.7 %; `logs-sidecar` streams the jsonlog; `promote`: replica promoted, first write after 6.4 s (Deployment scale-to-0 + pod deletion dominate; 0.5 s with `docker kill` on compose) |
| mysql | MySQL Shell dump 5 s | mysqlsh / mysqldump / clone verified; clone scratch Pod replayed the `source` Service's binlog until the GTID before the DELETE (PITR) | logging drill: slow query 0.6 s, general-log audit, overhead within noise |
| clickhouse | `BACKUP ... TO Disk('backups', 'cron/<ts>')` 5 s | single-replica, ON CLUSTER (drop + in-place RESTORE TABLE, verified on both replicas) and incremental | |
| cockroach | `BACKUP ... INTO 'nodelocal://1/cron'` 6 s, `SHOW BACKUPS` lists it | full / incremental / `AS OF SYSTEM TIME` PITR verified | |

`verify-backups postgres mysql clickhouse cockroach` -> 4/4 PASS. Restore times on k8s exclude image pull and pod scheduling
(`k8s_scratch.scratch_run` returns once the Pod is Running); on compose `docker run -d` returns before the process starts.

## Boilerplate notes

- A new engine needs: a `backup:` block in `lab.yaml` (volume, restore port), a row in `SPECS` of `gen-backup-addons.py`, a
  `sidecar_spec` line in `scenarios-backup.sh` if its logs live on a PVC, and (for the drills) the `harness/rdlab/backup/<engine>.py`
  strategies - the same file that drives the compose drills.
- Backup PVCs are ReadWriteOnce; the CronJob pod, the primary and the scratch restore pod all mount them on the single lab node.
  On a multi-node cluster use an RWX class (NFS/CephFS) or a bucket (`pg_basebackup` + WAL-G/pgBackRest to S3, BR/CockroachDB/ClickHouse
  to `s3://`) - the commands are the same, only the target changes.
- Secrets are inline in the generated manifests because the compose files carry lab passwords; for a real deployment move them into
  `Secret` objects and `envFrom`.
